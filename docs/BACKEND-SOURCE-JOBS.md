# Quarantined source upload and scan jobs

This batch adds authenticated CSV/XLSX original upload, asynchronous scan-job state, a dedicated restricted scanner role, real encrypted-storage retrieval and a ClamAV client. **No live malware scanner is configured or certified by these tests.** Files remain quarantined when scanning is unavailable; no provider success is simulated in the database.

## Upload and API

`POST /api/v1/tenants/:tenant/entities/:entity/source-files` accepts `application/octet-stream`, a known Content-Length from 1 byte to 50 MiB, and a percent-encoded filename in `X-Upload-Name`. Recent real MFA and entity-wide `imports.manage` are checked before reading the binary body and again before mutation. CSV must be UTF-8 without binary control characters; XLSX must have a ZIP local-file signature. This is preliminary type checking, not proof of a valid workbook. No formula or file content is executed. Detailed workbook parsing must occur after scanning in an isolated parser.

The original is AES-256-GCM encrypted in the existing private Neon bucket, decrypted and hash-verified before registration, and queued once by file SHA-256 plus entity. Reuploads reuse the source and job. Deleted/infected/rejected sources cannot be reused. Existing financial/bank draft imports can explicitly request scanning through `POST .../source-files/:id/scan` with `{}`. Normal runtime credentials cannot update scan status.

`GET .../source-files` returns at most 100 metadata entries to import-authorized users. `GET .../jobs/:id` returns status, progress, attempts, safe error code and trace ID. `POST .../jobs/:id/cancel|retry` requires a reason and UUID request key. Terminal history is preserved; a failed quarantined scan can retry up to three total attempts, and a replay reuses its result. Cancellation of a queued job stops dispatch; running cancellation wins over a late scan result. Scanning alone does not publish datasets or approve outputs.

## Worker and fencing

Migrations 015–017 add a private hashed lease store and narrow enqueue/control/claim/finalization functions. The dedicated `mizan_scanner_v1` role can execute only scan claim/finalization bridges, without reading user, financial, source or native identity tables. The API role cannot claim jobs or mark sources clean. Every worker attempt has a fresh random lease capability, a five-minute expiry and attempt number. Concurrent claims use row locks/SKIP LOCKED. Expired attempts are recorded immutably; a replacement fences out old/empty tokens. Job-control and claiming use consistent tenant-capacity serialization without waiting in the reverse lock order.

Conservative infrastructure limits are 10 queued/running jobs per tenant, two concurrent scans per tenant and three attempts per job. These limits do not implement subscription billing/usage policy. Worker checks enforce current tenant/entity activity and requester permissions, including global account suspension, again before accepting a result. Attempt records are inserted once on completion or lease expiry because that business table is append-only.

`npm run worker:scan -- --once` processes one claim; omit `--once` for the local polling loop. Its SQL connection is `SCANNER_DATABASE_URL`, generated by `backend:setup`. Store only scanner credentials, source encryption key and private bucket access in a deployed worker's secret configuration. Development uses `.env.local`; the implementation removes owner/application/identity URLs and the identity secret from its process environment before processing. A split production secret file/host and hardened worker deployment still need operational configuration. This trusted storage/scanner broker is not the untrusted file parser.

## Real scanner configuration

Configure an actual local `clamd` socket with `CLAMAV_SOCKET`, or loopback TCP with `CLAMAV_HOST` and `CLAMAV_PORT`. Arbitrary public TCP endpoints are rejected, so financial file contents cannot be redirected to an unapproved remote scanner. The client follows the official [ClamD INSTREAM protocol](https://docs.clamav.net/manual/Usage/ClamdProtocol.html): length-prefixed chunks, a terminating zero chunk and NUL-delimited results. It retrieves the engine/signature version first, requires a valid signature timestamp no older than `CLAMAV_MAX_SIGNATURE_AGE_HOURS` (default 24), and rejects timeouts, stale signatures, truncated responses, protocol/size errors and missing configuration. Only an exact `stream: OK` permits a clean outcome; an explicit `FOUND` outcome quarantines the source as infected and fails the job. Engine/signature updating, supported release selection, network controls and monitoring need activation and real acceptance tests.

## Evidence and remaining work

- `server/clamav-client.test.mjs`: TCP protocol fixtures for chunk fidelity, clean/infected interpretation, missing/stale versions, denied public endpoints and scanner errors. These are transport contract tests, not live scanner accuracy evidence.
- `verification/scan-jobs-api.json`: actual native MFA, encrypted original storage, duplicate upload/job prevention, unavailable-provider failure, dedicated-role denial, retry/cancellation, concurrent claims and expired/null-token fencing. No source is marked clean by the suite.
- `verification/scan-job-authority.json`: global suspension blocks retained grants and cancels queued work; the complete controlled fixture is rolled back.
- `verification/scan-jobs-browser.json`: real source/job states and persistence across five widths.

The source/job UI displays quarantine, task status/attempts, scanner unavailability and explicit retry/cancel actions. Full FR-006/013 acceptance is still open: real scanner deployment with benign/malicious/archive samples; isolated bounded CSV/XLSX/GL parsing; scan-first replacement of the legacy structurally parsed draft import endpoints; worksheet preview/mapping/corrections/publication; cancellation of every downstream job; plan quotas, orphan-object cleanup, monitoring, crash/recovery/load/security acceptance and production deployment.
